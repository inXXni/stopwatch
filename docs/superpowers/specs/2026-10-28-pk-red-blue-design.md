# PK 模式红蓝对阵设计文档

日期：2026-10-28
基础：`2026-10-27-pk-mode-design.md`（下称「PK 设计」）

## 1. 背景与目标

PK 模式上线后的反馈：屏幕上感受不到是在 PK。现在的画面就是两块同色秒表上下叠在一起，
没有任何东西在说「这是两个对手」，也看不出「现在轮到谁」。

选手背对屏幕按蓝牙键盘，屏幕朝着裁判和观众（见 PK 设计第 2 节），
所以竞争感是做给观众看的。本次改动只动 PK 模式的外观，不改流程：

- 两格分成红方和蓝方，中间用「VS」隔开
- 每格左侧加一根色条，用闪烁提示轮到谁、谁正在计时

## 2. 讨论过、没采用的方向

- **LED 比分牌**（左侧选手编号框 + 轮次箭头，保持全红）：编号「1」「2」不如红蓝对立
  那样一眼就是对手；编号框还要占宽度，iPad 上数字会被挤小。
- **裁判判胜 + 局分**（裁判按键判定胜方，赢家高亮、输家变暗，累计比分）：竞争感最强，
  但要推翻 PK 设计里「程序不判胜负、不统计」的非目标，范围明显变大。以后可以叠加在
  红蓝对阵上做，本次不做。
- **停表时数字闪两下**：试过 120ms 和 250ms 两种节奏，最终不要。停表后数字立即定格，
  锁定时间维持 500ms。
- **色条紧贴数字左边**（色条画进数字的 SVG 里，与数字一起缩放）：实现简单，但横屏时
  色条会从屏幕最左边挪到数字旁边。对比演示后选择保留在屏幕最左边，只让高度跟着数字走。

## 3. 非目标（明确不做）

- 停表闪烁或其他任何停表动效
- 「红方」「蓝方」「P1」「P2」之类的文字标签：颜色和位置已经说明身份
- 程序判定胜负、记录局分
- 计时中的那一格放大、已定格的那一格缩小（PK 设计第 3 节的结论不变）
- 普通模式的任何变化：不带 `?pk` 时外观与行为和现在完全一致

## 4. 配色

| | 上格 | 下格 |
|---|---|---|
| 阵营 | 红方 | 蓝方 |
| 数字与色条 | `#ff2d2d`（即现有的 `--ink`） | `#3d8bff`（暂定） |
| 幽灵层 | 红色，透明度沿用 `--ghost-opacity` | 蓝色，透明度同左 |

- 每格的颜色在待机、计时中、已定格三种状态下都不变，与现在「三态同色」的规则一致。
- 蓝色在黑底上天然显得比红色暗，两方亮度不等会削弱公平感。暂定的 `#3d8bff`
  相对亮度 0.267，与红色 `#ff2d2d` 的 0.233 接近；更深的 `#2d6bff` 只有 0.183。
  最终色值在手机真机上与红色并排比较后确定，以「看起来一样醒目」为准。
- 两种颜色定义为 CSS 变量，例如 `--ink-red` 与 `--ink-blue`，不在规则里写死色值。

## 5. `?green` 在 PK 模式下不生效

红蓝是阵营色，停表变绿会把蓝方（或红方）的身份抹掉，因此 PK 模式下忽略 `?green`：

- PK 模式下两格始终显示各自的阵营色。「停没停」靠数字是否跳动来区分。
- `?green` 只对普通模式生效，行为不变。
- `?pk&green` 按 `?pk` 处理：`index.html` 头部选 manifest 的脚本在 PK 时一律选
  `manifest-pk.json`，iOS 的 `apple-mobile-web-app-title` 一律为「PK 秒表」。
- 删除 `manifest-pk-green.json`，同时从 `tools/make-manifests.mjs` 的 `VARIANTS`
  与 `sw.js` 的 `ASSETS` 中移除。已安装的「PK 秒表 绿」图标（如有）打开的是
  `./?pk&green`，按上一条会正常进入 PK 模式，只是不再有单独的 manifest 匹配它。
  用户目前的手机上装的是「PK 秒表」，不受影响。

## 6. 布局

> 2026-10-28 起 VS 与色条的排法按屏幕区分：宽屏横屏改为色条脊柱，竖屏 VS 放大，
> 其余横屏不变，详见 `2026-10-28-pk-vs-spine-design.md`。本节描述的是改动前的样子，
> 「字号代价」表格是当时的实测。

### VS 分隔条

两格之间插入一条分隔条，仅在 PK 模式下显示：

- 高度 `8vmin`
- 正中是「VS」两个字母，琥珀色 `#ffb020`，字号约 `5vmin`
- 「VS」左右各一段细横线，颜色为暗灰（约 `#3a3a3a`），两端不顶到屏幕边缘

### 左侧色条

每格左侧一根竖向色条，仅在 PK 模式下显示：

- 宽 `1.5vmin`，圆角，垂直居中
- 高度与数字（幽灵层 `88.88`）的实际渲染高度相同
- 与数字之间留 `2.5vmin` 间距；色条加间距共占 `4vmin` 宽，数字区相应变窄
- 颜色与该格阵营色相同

**高度为什么要量出来，而不是按格子高度的比例给。** 最初定的是「格子高度的 80%」，
横屏时数字基本撑满格子，看不出问题；竖屏时数字受屏幕宽度限制变得很矮（手机竖屏
数字高 94px，格子高 325px），色条就明显比数字长。数字的实际高度由格子宽高与 viewBox
共同决定，CSS 算不出来，所以由 `app.js` 读取幽灵层的渲染高度写给色条：

- `display.js` 每次重新设定 viewBox（字体加载完成、超过 99 秒读数加宽）后调用 `onFit` 回调
- `ResizeObserver` 盯着两个格子，转屏、窗口缩放时重新量
- 量到之前色条高度为 0，不显示，避免先闪出一根错误长度的色条

### 字号代价

分隔条占高度，色条占宽度，PK 模式下数字会比改动前小一些。下表是在 headless Chrome 里
实测的幽灵层 `88.88` 渲染宽度（CSS 像素），改动前后对比：

| 屏幕 | 改动前数字宽（实测） | 改动后数字宽（实测） | 缩小 |
|---|---|---|---|
| 手机横屏 800×360 | 482 | 441 | 8.5% |
| iPad Air 横屏 1180×820 | 1075 | 1002 | 6.8% |
| iPad 横屏 4:3 1024×768 | 928 | 899 | 3.1% |

实测与按七段数字宽高比 3:1 的估算（9%、7%、3%）相差不到 1 个百分点。
这是为了让画面一眼看出「对阵」而付出的代价，可以接受。

PK 设计的验收标准第 8 条「iPad 横屏（4:3）下分屏前后数字尺寸一致」因此作废，
改为本文档第 9 节的条款。

## 7. 轮次提示

### 每格的四种状态

PK 设计里每格有三种状态（`empty` 空、`running` 计时中、`done` 已定格）。
本次在「空」里分出一种「轮到这一格」，记作 `next`：

| PK 状态 | 上格（红方） | 下格（蓝方） |
|---|---|---|
| `WAIT_P1` | `next` | `empty` |
| `RUN_P1` | `running` | `empty` |
| `LOCK_P1` | `done` | `empty` |
| `WAIT_P2` | `done` | `next` |
| `RUN_P2` | `done` | `running` |
| `LOCK_P2` | `done` | `done` |
| `RESULT` | `done` | `done` |

`LOCK_P1` 期间下格仍是 `empty`：500ms 锁定期内拍击无效，这时提示蓝方「该你了」
会误导；锁定结束进入 `WAIT_P2`，蓝方色条才开始闪。

### 色条的显示

| 该格状态 | 色条 |
|---|---|
| `next` | 呼吸闪烁：透明度在 1 与 0.15 之间往返，单程 0.8 秒 |
| `running` | 呼吸闪烁，与 `next` 相同 |
| `done` | 常亮 |
| `empty` | 暗，透明度 0.2 |

色条从轮到这一格开始闪，一直闪到停表才常亮。`next` 与 `running` 用同一条 CSS
`animation`，状态切换时浏览器不会让动画重新起跳，开始计时那一拍闪烁节奏是连贯的。

数字本身在四种状态下的显示规则不变，只有色条随状态变化。

### 普通模式

普通模式不显示色条，`next` 状态只在 PK 模式出现。`slotStateOf`（普通模式的映射）
不变；改动的是 `pkSlotStates`。

## 8. 测试策略

纯逻辑部分用 `node --test` 覆盖：

- `pkSlotStates`：按第 7 节的表格覆盖全部 7 个 PK 状态，重点是
  `WAIT_P1` 上格为 `next`、`LOCK_P1` 下格仍为 `empty`、`WAIT_P2` 下格为 `next`
- `slotStateOf`：普通模式的映射不变，原有测试保持通过
- manifest 测试：`VARIANTS` 只剩三份；`?pk&green` 对应 `manifest-pk.json`；
  `sw.js` 的 `ASSETS` 不再含 `manifest-pk-green.json`，且仍包含其余全部 manifest

外观部分（红蓝配色、分隔条、色条闪烁、字号）在真实浏览器与手机真机上验证。
蓝色的最终色值在真机上定。

改动发布时 `sw.js` 的 `CACHE` 版本号加一。

## 9. 验收标准

1. 不带 `?pk` 时，外观与行为和现在完全一致：单格、全红、无色条、无分隔条，`?green` 照常生效
2. 带 `?pk` 时，上格数字为红色，下格数字为蓝色，两格之间有带「VS」的分隔条
3. 两格左侧各有一根与数字同色的色条，横屏、竖屏下都与数字一样高，转屏后跟着变
4. 等红方拍及红方计时中，红方色条闪烁、蓝方色条变暗；红方停表后红方色条常亮，锁定期内蓝方仍暗
5. 红方锁定结束后蓝方色条开始闪烁，一直闪到蓝方停表；之后两根色条都常亮
6. `?pk&green` 打开后与 `?pk` 完全一致，停表不变绿
7. 停表后数字立即定格，不闪烁；500ms 锁定期不变
8. 手机真机上红蓝两色看起来一样醒目
9. 手机横屏与 iPad 横屏下数字缩小幅度与第 6 节的实测值相当
10. 全部 `node --test` 测试通过
