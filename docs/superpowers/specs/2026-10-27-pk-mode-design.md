# PK 模式设计文档

日期：2026-10-27
基础：`2026-10-27-slap-stopwatch-design.md`

## 1. 背景与目标

一种现场游戏：裁判口头报出一个目标秒数（例如 5 秒 20），两名选手依次盲拍计时器，
谁拍出的成绩更接近目标谁获胜。

秒表因此需要同时留住两个人的成绩：第一名选手停表后结果留在屏幕上，
第二名选手接着在同一块屏幕上计时，两人成绩并排供裁判和观众比对。

## 2. 盲拍如何实现

**不通过软件隐藏数字。** 选手拍的是外接蓝牙小键盘的 Enter 键，
屏幕背对选手、朝向裁判与观众。选手看不见读数，观众却能全程看着数字飞转。

这比在计时过程中遮住数字更好：遮住会让观众也失去看点，而且会让人怀疑表没启动。
现有显示逻辑因此完全不需要改动。

## 3. 非目标（明确不做）

- 不接收目标秒数，不计算误差，不判定胜负——屏幕只负责留住两个成绩，由裁判比对
- 不支持三名及以上选手
- 不记录历史、不统计、不排名
- 计时中不做任何形式的数字隐藏
- 不做字号动态变化（例如计时中的一格放大、已定格的一格缩小）：
  切换选手时数字会突兀地缩放，且两人字号不等会削弱结果展示的公平感

## 4. 进入方式

通过 URL 查询参数 `?pk` 进入，与现有的 `?green` 同一套机制。

这样可以把普通秒表与 PK 版分别安装到桌面，得到两个互不干扰的图标，名字分别是
「秒表」和「PK 秒表」。这依赖每种参数组合各有一份写明 `start_url` 的 manifest，
细节见 `2026-10-27-slap-stopwatch-design.md` 的「安装与参数」一节。
不在界面上做开关：整块屏幕都是拍击区，任何按钮都可能被误拍。

## 5. 布局

两格上下平分，上格为第一名选手，下格为第二名。

**不显示 P1/P2 文字标签。** 位置本身即身份，省下的空间全部留给数字。

### 为什么是上下分屏而不是左右

七段数字的宽高比约为 3:1，屏幕越扁，上下分屏的代价越大，但左右分屏在任何
横屏比例下都更差。以手机横屏（844×390，可用区 812×358）为例：

- 上下分屏：每格 812×179，数字宽 542
- 左右分屏：每格 406×358，数字宽 406

### 每格的视觉状态

> 2026-10-28 起改为红蓝对阵，详见 `2026-10-28-pk-red-blue-design.md`，本节已按改动后的规则更新。

上格是红方，下格是蓝方，每格左侧有一根同色色条提示轮次，两格之间有「VS」。
VS 与色条的排法按屏幕区分（宽屏横屏为色条脊柱），见 `2026-10-28-pk-vs-spine-design.md`。

| 该格状态 | 数字 | 色条 |
|---|---|---|
| 尚未轮到 | 阵营色，显示 `00.00` | 暗 |
| 轮到这一格 | 阵营色，显示 `00.00` | 呼吸闪烁 |
| 计时中 | 阵营色，读数跳动 | 呼吸闪烁 |
| 已定格 | 阵营色 | 常亮 |

数字在各状态下都是阵营色，待机那格不做暗显——实物 LED 牌待机时也是亮着的。

`?green` 只对普通模式生效。PK 模式下停表变绿会盖掉阵营色，因此忽略这个参数，
`?pk&green` 与 `?pk` 完全一致。

### 字号代价

上下切开后，每格的宽高比若仍大于数字的 3:1，数字就受格子高度限制而缩小。
临界点约为屏幕可用区 3:2：

| 屏幕 | 单人时 | 分屏后每人 | 损失 |
|---|---|---|---|
| iPad 横屏 4:3 | 1114×369 | 1114×369 | 0% |
| 电视/投影 16:9 | 1834×607 | 1501×497 | 18% |
| 手机横屏 19.5:9 | 813×269 | 542×179 | 33% |

比 3:2 更方的屏幕分屏零损失，更扁的屏幕越扁代价越高。
设备以横屏平板为准，手机横屏可用但字会小一圈。

红蓝对阵加入的 VS 分隔条与色条会让数字再小一些：手机横屏约 8.5%，iPad 横屏约 3%–7%，
见 `2026-10-28-pk-red-blue-design.md` 第 6 节。

之后的 VS 色条脊柱改动让宽屏横屏的两行靠拢，手机横屏数字从 441 回升到 467，
iPad 横屏不变，见 `2026-10-28-pk-vs-spine-design.md`。

## 6. 状态机

PK 模式有独立的状态机，不复用普通模式的四状态机——两者在「停表后再拍一下」
这个关键转移上语义不同：普通模式总是清零，PK 模式第一次停表后是换下一个人。

| 状态 | 上格 | 下格 | 拍击后 |
|---|---|---|---|
| `WAIT_P1` | 空 | 空 | → `RUN_P1` |
| `RUN_P1` | 计时中 | 空 | → `LOCK_P1` |
| `LOCK_P1` | 定格 | 空 | 忽略（锁定期内） |
| `WAIT_P2` | 定格 | 空 | → `RUN_P2` |
| `RUN_P2` | 定格 | 计时中 | → `LOCK_P2` |
| `LOCK_P2` | 定格 | 定格 | 忽略（锁定期内） |
| `RESULT` | 定格 | 定格 | → `WAIT_P1`（清场） |

`LOCK_P1` 与 `LOCK_P2` 在 500ms 后分别自动转入 `WAIT_P2` 与 `RESULT`，
与普通模式的锁定窗口一致，用途相同：挡掉手掌反弹与多指造成的二次触发。

### 出结果后为何要分两拍

`RESULT` 状态下拍击只清场、不开始计时，必须再拍一下才开始新一轮。
现场刚宣布完胜负，人容易兴奋手快；若一拍就重来，还没记录的成绩会被直接抹掉。

## 7. 显示层重构

当前显示逻辑（幽灵层 + 读数层 + viewBox 测量）硬编码为页面上唯一的一组元素。
PK 模式需要两组，因此把这部分封装成可实例化的单元：给定一个 `<svg>`，
返回一个带 `render(text)` 方法的对象，自己管理幽灵层、读数层与 viewBox 测量。

普通模式创建一个实例，PK 模式创建两个。普通模式下第二格以 CSS 隐藏，
第一格占满整屏，外观与行为与现状完全一致。

## 8. 测试策略

PK 状态机是不依赖 DOM 的纯函数，用 `node --test` 覆盖全部状态与输入的组合，
重点是三处容易写错的转移：

- `LOCK_P1` / `LOCK_P2` 状态下拍击被忽略
- `WAIT_P2` 状态下拍击开始的是下格而非重开上格
- `RESULT` 状态下拍击只清场，不进入 `RUN_P1`

布局与视觉通过真实浏览器验证。

## 9. 验收标准

1. 不带 `?pk` 时，行为与外观和现在完全一致，只有一格且占满整屏
2. 带 `?pk` 时上下两格平分，上格先计时
3. 上格停表后读数定格不动，拍击可让下格开始计时
4. 下格计时期间，上格读数始终保持不变
5. 两人都完成后，拍一下只清空、不开始计时，再拍一下才开始新一轮
6. 每次停表后的 500ms 内拍击无效
7. `?pk&green` 与 `?pk` 完全一致，停表不变绿（2026-10-28 起，原为两格各自变绿）
8. iPad 横屏（4:3）下数字只因 VS 分隔条与色条略微缩小（约 3%），不因上下分屏本身而缩小
