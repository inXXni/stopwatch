# 「咚」放大设计文档

日期：2026-10-29
基础：`2026-10-29-stop-burst-design.md`（下称「爆裂设计」）第 4 节「低音咚」

## 1. 背景与目标

用户在手机上觉得停表的「咚」不够劲，而且「滴」比「咚」响得多。原因：

- 「滴」是 2461 Hz，正好是人耳与手机喇叭最灵敏的频段，又稳稳响 0.4 秒
- 「咚」的能量主要在 70～300 Hz，手机喇叭放不出来，人耳也不敏感，0.1～0.2 秒就衰减完

模拟手机喇叭（滤掉 380 Hz 以下）再按 A 计权量 0～0.4 秒的有效值：「滴」−9.4 dB，「咚」−32.6 dB。

用户在手机试听页里比较了六种配方、五档音量、提亮与否、停表时「滴」的四种处理后选定：

- **配方**：不变，就用现在的「咚」
- **音量**：「爆表」，即「咚」的音量放大 3 倍，只加在「咚」上
- **不提亮**
- **「滴」原样**

## 2. 放大多少

| 部分 | 原来 | 现在 |
|---|---|---|
| 三角波的峰值增益 | 0.7 | 2.1 |
| 敲击噪声的增益 | 0.5 | 1.5 |

音高、包络时间、敲击噪声的长度与低通都不变（见爆裂设计第 4 节）。

## 3. 共用出口：软限幅

增益 2.1 远超数字满幅 1.0，直接送到喇叭会被硬削顶，「滴」叠在上面也跟着破音。
所以「滴」和「咚」都先经过一个共用出口，再送到喇叭：

- 幅度 |x| ≤ 0.5：原样通过。「滴」的峰值就是 0.5，所以「滴」一点不变
- |x| > 0.5：`0.5 + 0.45 × tanh((|x| − 0.5) / 0.45)`，正负对称，最高趋近 0.95（约 −0.45 dBFS）

「咚」开头被软压成接近方波，多出来的泛音落在手机喇叭放得出的频段，这正是它在手机上变响的原因。
同样的 A 计权量法下，「咚」从 −32.6 dB 升到约 −25.6 dB，开头 0.15 秒从 −28.3 dB 升到约 −21.4 dB。

### 实现方式

`WaveShaperNode`，曲线 4096 个点，覆盖输入 −4～4；送进去之前先乘 1/4，
因为 WaveShaper 把输入的 −1～1 映射到整条曲线。超过 ±4 的输入落在曲线两端，即 ±0.95。

**不做过采样**（`oversample = 'none'`）。过采样时的重采样滤波会让输出峰值冲过 0.95，
在系统输出端被硬削，出「咔」声；试听页里测到过。

出口在第一次发声时随音频环境一起建，之后一直复用。

### 为什么不用别的办法

- 只把增益乘 3、不加出口：硬削顶，「滴」叠在上面也破音，和试听时听到的不一样
- 用 `DynamicsCompressorNode` 当限幅器：它自带补偿增益，还会在「咚」响时把「滴」一起压下去

## 4. 不变的部分

- 「滴」的频率、包络、音量，以及「除清屏那一拍外每拍都响」的规则
- 「咚」只在停表那一拍响，与「滴」同时开始、互不打断
- 「咚」不受「减弱动态效果」影响
- 没有 Web Audio 或音频出错时静默跳过，不影响计时

## 5. 不做

- 换配方（试过的重鼓、双层重拳、爆裂轰、低音长尾都不要）
- 提亮（2.5 kHz 加 6 dB）
- 停表那一拍的「滴」减半、缩短或不响
- 音量设置界面

## 6. 测试

`node --test`：

- 软限幅曲线：0.5 以内原样通过；超过 0.5 单调递增、正负对称、不超过 0.95，输入 4 时已接近 0.95
- 「滴」与「咚」（三角波和敲击噪声）都接到同一个出口，出口经 WaveShaper 接到喇叭；
  WaveShaper 曲线 4096 点、不做过采样；出口只建一次
- 「咚」的三角波峰值增益 2.1、敲击噪声增益 1.5
- 原有测试不变：频率、0.32 秒停、不打断「滴」、没有 Web Audio 时静默跳过

无头 Chrome，用真的 `beep.js` 离线渲染：

- 「滴」单独渲染，与改动前的 `beep.js` 逐个采样比较，差别在浮点误差以内
- 「滴」与「咚」一起渲染，峰值不超过 0.95
- 「咚」模拟手机喇叭并 A 计权后的有效值与试听页里「现在·爆表」一致（约 −21.4 / −25.6 dB）

## 7. 验收标准

1. 停表那一拍的「咚」在手机上明显变响，音色与原来同一种
2. 「滴」听起来与原来完全一样
3. 「滴」和「咚」叠在一起不破音、没有「咔」声
4. 其余拍击、清屏、锁定期的声音规则不变
